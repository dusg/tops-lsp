# 功能规格说明：Tops C++ 的基础语言功能（错误提示、补全、悬停）

**特性分支**：`007-core-language-closure`

**创建日期**：2026-10-19

**状态**：草稿

**输入**：用户原话："实现 Tops C++ language server 的“基础语言功能闭环”。新增 diagnostics、completion 和 hover，并以已实现的 definition、references、document symbols 为前提验证端到端闭环；明确每个请求的输入、结果、空结果、错误、取消和 stale 行为。验收必须覆盖一个可编辑的 Tops kernel 文件、一个标准 C++ 语法/语义错误文件和一个 Tops 扩展语义错误文件。"

## 这份文档讲什么

- **给谁看**：实现这个功能的开发者、写测试的人、评审的人。读之前不需要懂语言服务器协议。
- **现在缺什么**：服务器已经能跳转到定义、查引用、列出文件里的符号。但用户写代码时最常用的三件事还没有：看到错误提示、输入时有候选名字、鼠标停在名字上能看到类型信息。
- **做到什么算完成**：用户打开一个 Tops kernel 文件，能边写边看到错误、能补全、能悬停看信息；改完代码后这些结果跟着更新，不会显示旧内容。并且准备好三个测试文件，分别代表“正常 kernel”“标准 C++ 写错”“Tops 规则写错”。

## 名词解释

| 词 | 通俗解释 |
|----|----------|
| 语言服务器 | 编辑器背后的程序。编辑器把文件内容和光标位置发过来，它把结果发回去。 |
| 诊断（diagnostics） | 问题面板里的一条提示，例如“缺少分号”“类型不匹配”。 |
| 补全（completion） | 敲代码时弹出的候选名单。 |
| 悬停（hover） | 鼠标停在某个名字上时弹出的说明框。 |
| 定义（definition） | 跳到名字声明的地方。 |
| 引用（references） | 列出某个名字被用到的所有位置。 |
| 文档符号（document symbols） | 编辑器侧边栏里显示的函数、变量清单。 |
| 分析 | 服务器把当前文件读一遍，算出符号、类型和错误。 |
| 文档版本 | 编辑器每改一次文件，版本号加一。用来判断结果是不是最新的。 |
| 一次分析的结果 | 针对某个文档版本算出来的符号、错误和类型信息。 |
| 过期结果（stale） | 针对旧版本算出来、但文件已经变了的结果。必须丢掉，不能显示给用户。 |
| 语法错误 | 代码结构不成立，例如括号没配对、少分号。 |
| 语义错误 | 结构成立但意思不成立，例如用了没声明的名字。 |
| Tops 扩展规则 | 普通 C++ 之外、Tops 编译器额外要求的规则，例如 host 函数和 device 函数能不能互相调用、指针指向哪块内存、向量宽度限制。 |
| 上下文 | 判断 Tops 规则要用到的环境信息：目标芯片代际、编译参数、头文件路径、宏等。 |
| 上下文不完整（降级） | 环境信息缺一部分，服务器没法可靠判断 Tops 规则。这时只做标准 C++ 检查，并提示用户“Tops 规则未生效”。 |
| 严重级别 | 问题面板里的等级：Error（真错误）、Warning（警告）、Information（提示）。 |
| 诊断编号（code） | 每条诊断自带的短字符串，例如 `syntax-error`。测试和客户端靠它区分问题类型，不靠中文消息。 |
| profile / pass | profile 是目标配置（例如 GCU400 默认配置）；pass 是分析视角（host 侧或 device 侧）。同一个文件在两个视角下可能得出不同结论。 |
| 来源记录（provenance） | 说明这条结论从哪来：来自编译数据库、来自默认配置，还是来自工具链内建规则。 |
| 测试固定输入（fixture） | 测试用的固定文件，以及它对应的预期结果。 |

## 澄清记录

### 2026-10-19

- 问：文件已打开、但最新一次分析还没做完时，补全和悬停怎么办？
  答：两者都不报错、也不等分析做完，都告诉用户“正在分析”：悬停弹一条“正在分析中”的提示；补全名单里只放一条同样含义的提示项。
- 问：文件已打开、但最新分析还没完成时，跳定义、查引用、列符号应该等一下还是直接返回空结果？
  答：这三项继续等分析完成再返回结果，不改已有行为；只有补全和悬停立即返回“正在分析”提示。
- 问：三个验收测试文件要跑在哪一层？是只跑服务器进程的端到端测试，还是同时在包内做单元测试？
  答：只跑端到端进程测试，三个文件都通过真实服务器进程验证；这一版不为此另建包内单元测试。
- 问：三个验收测试文件从哪里取源码？是放到测试数据目录里作为固定文件，还是写在测试代码里当字符串？
  答：放到测试数据目录里作为固定文件，测试代码读取文件内容；同一个文件也能在编辑器里直接打开和修改。
- 问：首次打开文件、分析还没开始时，跳定义、查引用、列符号会一直等下去，要不要设一个等待上限？
  答：设固定上限 2 秒；到点还没分析完就返回标准 `ContentModified` 错误，让客户端稍后重试，不返回空结果。
- 问：悬停内容用什么格式？
  答：看编辑器在初始化时声明支持什么：支持 Markdown 就用 Markdown，只支持纯文本就用纯文本。
- 问：“上下文不完整”这条提示用什么严重级别？
  答：统一用 Warning；它不代表代码有错。
- 问：补全这一版放哪些名字？
  答：不按固定类别列白名单。按光标位置的语法规则和语义可见性判断：语法允许、语义可见的名字都可以出现在候选里（自己声明的名字、关键字、宏、Tops 内建变量等）。
- 问：“上下文不完整”这条提示用哪个诊断编号？
  答：新开一个专用编号 `tops-semantic-context-degraded`，具体原因写在消息和附加字段里。
- 问：诊断消息、悬停文字和补全详情这些给用户看的文字，用中文还是英文？
  答：全部用英文，与现有代码里的诊断消息、日志和错误信息保持一致，不出现中英混排。

## 用户场景与测试

### 场景 1：在 Tops kernel 文件里边写边得到反馈（优先级 P1）

**用户故事**：我打开一个 `.tops` 文件写 kernel。写的过程中，希望同时看到错误提示、补全候选和悬停信息，也能跳到定义、查引用、看文件里的符号清单。改完代码后，这些结果要跟着更新。

**为什么排第一**：这是本功能的主要价值。只有这几项基于同一份最新分析结果一起工作，用户才不用切到别的工具去确认名字和类型。

**怎么单独验证**：准备一个能正常分析的 Tops kernel 测试文件。按顺序做：打开文件 → 请求补全 → 悬停 → 跳定义 → 查引用 → 列符号 → 改一行 → 再请求一次。检查每一步的结果是不是来自最新版本。

**验收场景**：

1. 文件已打开且分析完成时，用户请求诊断、补全、悬停、定义、引用、文档符号：诊断应为空或只有已核实的信息项；补全给出当前可见的名字；悬停给出名字、种类、已知类型或签名、来源；定义跳到声明处；引用列出所有使用处；文档符号列出已识别声明。
2. 用户新增一个声明并更新到新版本：新版本分析完成后，补全里出现新名字，悬停用新类型，定义、引用、文档符号都反映新版本；任何结果都不能来自旧版本。
3. 光标在空白、注释或字符串里：补全返回空名单，悬停返回空结果，都不报错。
4. 上下文信息齐全（状态为 `resolved`）且明确了 profile 和 pass 时，悬停一个 Tops 声明或内建名字：悬停内容要写明用的是哪个 profile、哪个 pass，并分开标注哪些是标准 C++ 结论、哪些是 Tops 扩展结论。

---

### 场景 2：标准 C++ 写错时给出稳定的错误提示（优先级 P1）

**用户故事**：我写标准 C++（不一定涉及 Tops 特性）时写错了，例如少分号、用了没声明的名字、类型对不上。我希望错误提示指的位置准确、编号固定、级别正确；我把错误改好后，提示要消失。

**为什么和场景 1 同级**：语法和语义错误是编辑过程中最常见的反馈。如果位置、版本或清理不可靠，补全和悬停的结果也不可信。

**怎么单独验证**：准备一个包含标准 C++ 错误的测试文件，检查诊断的编号、位置、严重级别、版本字段；改正后再检查旧提示是否被清掉。

**验收场景**：

1. 文件有确定的语法错误：分析完成后，发布一条诊断，带固定语法编号、Error 级别、准确的代码范围，版本字段对应当前分析。
2. 文件语法完整但有已核实的标准 C++ 语义错误（例如没声明的名字、明显的类型不匹配）：发布一条带固定语义编号、Error 级别、准确范围的诊断。
3. 用户把错误改正成有效代码：新版本分析完成后，当前文件的问题清单里不再包含旧错误，用户看不到旧提示。
4. 文件有语法或语义错误时，用户请求补全、悬停或导航：仍能解析的符号照常给结果；无法解析的位置给空结果；服务器不能崩溃，也不能返回不符合标准的错误。

---

### 场景 3：Tops 规则写错时只报有把握的错误（优先级 P1）

**用户故事**：我写的代码违反了 Tops 特有规则，例如 host 函数直接调用 device 函数、指针用错了内存空间、向量宽度不合法。我希望看到明确的提示；但如果服务器拿不到目标信息，我不希望它瞎猜。

**为什么和场景 1 同级**：这是 Tops 语言服务器和普通 C++ 工具的区别所在。判断错方向（把别的芯片规则套过来）比不提示更糟。

**怎么单独验证**：准备一个违反 Tops 规则的测试文件，分别给足环境信息、只给一部分、完全不给，检查提示的编号、级别、位置和来源记录。

**验收场景**：

1. 环境信息齐全（`resolved`）且有明确 profile 和 pass，文件确实违反了 Tops 规则：发布对应 `tops-semantic-*` 编号的 Error，范围覆盖出错的表达式或声明，并写明 profile、pass 和来源记录。
2. 同样的错误代码，但环境信息只有一部分（`partial`）或缺关键信息：不发布确定的 Error；最多发一条“上下文不完整”的提示。
3. 文件使用的是合法的 Tops 写法：不发布 Tops 相关的 Error；补全、悬停、导航结果都要带上来源记录。
4. 把同一份代码切到另一个已有明确配置的 profile 或 pass：只有受影响的 Tops 结论和提示变化，标准 C++ 结果照常可用，不能把别的芯片规则套过来。

---

### 场景 4：所有请求的行为规则一致（优先级 P2）

**用户故事**：作为维护者或客户端开发者，我希望每个请求的规则都一样清楚：需要传什么参数、成功时返回什么、没结果时返回什么、参数错了报什么、取消怎么表示、过期结果怎么处理。新增的补全和悬停要遵守，已有的定义、引用、文档符号也要遵守。

**为什么排第二**：规则一致，客户端才能稳定展示，测试才能覆盖失败情况。规则不一致会表现为编辑器闪烁、旧结果盖住新结果、或者请求一直不返回。

**怎么单独验证**：对每个已实现的方法，准备六类用例：正常输入、空结果、参数错误、取消、版本竞争、未实现方法。检查返回类型、错误码、结果内容，以及有没有混进旧版本数据。

**验收场景**：

1. 参数缺文档地址、位置格式不对、或位置超出文件范围：返回标准 `InvalidParams` 错误，不返回半截结果。
2. 请求的文件没有打开、也不在工作区：返回空结果，不报错。空结果的具体形式按方法区分：定义和悬停返回空值；引用、文档符号、补全返回空名单。
3. 请求还没算完就被取消：返回标准的“请求已取消”错误，不发结果。如果结果在取消到达前已经算完，可以正常返回结果。
4. 请求处理过程中文档版本或上下文版本变了，服务器只拿得到旧的分析结果：按方法返回空结果，不能返回旧数据。如果最新结果已经可用，就返回最新结果。这里要和“分析还没完成”区分开：前者是已有失效结果，返回空结果；后者是还没有结果，跳定义、查引用、列符号最多等 2 秒，超时返回 `ContentModified`。
5. 客户端请求这一阶段没实现的“拉取式诊断”方法：返回标准 `MethodNotFound`，不要假装支持。
6. 定义、引用、文档符号这些已有功能跑同一套用例：空结果、错误、取消、过期处理的规则要和新增方法一致，并且不能把不同版本的分析结果混在一起。
7. 文件刚打开、最新分析还没完成时同时发六个请求：补全只返回一条“正在分析中”提示项，悬停返回同类提示；跳定义、查引用、列符号在 2 秒内等到分析完成就正常返回结果，超过 2 秒则返回标准 `ContentModified` 错误；都不把旧版本结果当成新结果。

---

### 边界情况

- 空文件、只有空白或只有注释：诊断不崩溃；补全返回空名单；悬停和定义返回空结果；引用和文档符号返回空名单。
- 光标在文件末尾、最后一行之后、或名字中间：补全使用稳定的替换范围；悬停和定义按当前名字边界处理，判断不了就返回空结果。
- 文件用 CRLF 换行、含制表符、含中文或 emoji：诊断、补全、悬停、导航都按同一套位置换算，跨行范围不能偏。
- 正在输入、声明或函数签名还没写完：诊断标成“可恢复”或“未完成”；已识别的名字仍可用于补全、悬停和导航；不能因为当前写了一半就把整个旧索引清空。
- 用户连续快速修改：只发布最终版本对应的诊断；旧版本请求返回空结果；不能出现旧提示盖住新提示。
- 相关头文件变了：依赖它的旧结果作废；新分析完成前，不返回旧的诊断、补全、悬停和导航结果。
- 还没有任何可用结果（刚打开文件、分析进行中）：悬停弹一条“正在分析中”的提示；补全名单里只放一条同样含义的提示项；跳定义、查引用、列符号最多等 2 秒，超时返回 `ContentModified`，不无限等待。
- 已有旧结果但已失效（文档或上下文变了）：导航直接返回空结果，不等待，也不返回旧数据；不要和上一条“还没有结果”混为一谈。
- 同一位置有多个分不清的候选：不要随便选一个；按已定义的歧义处理规则处理（报歧义或降级）。
- 同一个问题被多个阶段各报一次：合并成一条，不要在同一个范围重复显示。
- 补全或悬停落在注释、字符串、或判断不了的宏条件区域：返回空结果或降级结果，不能凭空给出名字。
- 文件被关闭、或整个工作区配置失效：清除受影响文件的诊断；后续请求按“文件未打开”处理。
- 取消和完成同时发生：按标准请求流程处理，同一个请求只响应一次。
- 记录日志时：只记能定位问题的分类信息，不记完整源码，不记凭据。

## 需求

每条需求前面的编号（例如 `FR-001`）供计划、任务和测试引用；正文是具体要求。

### 功能需求

#### 错误提示（诊断）

- **FR-001**：每次分析完当前文件后，服务器必须把问题清单发给编辑器，并带上文件地址、文档版本、上下文版本，让人能看出这是针对哪一版算的。
- **FR-002**：同一个文件的问题清单要把全部来源合并：语法错误、标准 C++ 语义错误、索引降级提示、Tops 扩展语义错误，以及上下文状态提示（归入 Tops 扩展来源）。合并后的顺序要固定，同样输入每次结果一致。
- **FR-003**：完全一样的问题（编号、位置、级别、文字都相同）只显示一条，不能重复。
- **FR-004**：每条问题必须带代码范围、严重级别、来源标识、固定编号、可读文字；有关联位置（比如“在这里声明”）也要带上。诊断消息、悬停文字、补全详情、日志和错误信息统一用英文，与现有代码保持一致，不得中英混排。
- **FR-005**：语法错误、已核实且确定不成立的标准 C++ 语义错误、已核实的 Tops 违规用 Error 级；无法消除候选歧义时用 Warning；上下文不完整或没有上下文时的提示统一用 Warning 级，不能把它当成确定错误。
- **FR-006**：标准 C++ 语法问题用已经登记的语法编号；Tops 扩展问题用 `tops-semantic-*` 编号，包括 host/device 调用边界、内存空间、向量约束三类；上下文状态提示用两个专用编号：完全没有目标信息时用 `tops-semantic-context-missing`，信息只有一部分或互相矛盾时用 `tops-semantic-context-degraded`；两个编号的具体原因都写在消息和标准附加字段里，都不复用索引降级的 `analysis-degraded`。
- **FR-007**：当新版本已经没有问题时，服务器必须给这个文件发一份空的问题清单，把旧提示消掉。
- **FR-008**：旧版本算出来的问题必须丢掉；不能发旧文档版本、旧上下文版本或已失效分析的提示，也不能把不同版本的提示混在一起发。
- **FR-009**：文件关闭或整个上下文失效时，必须清掉受影响的诊断，并带上当前可用的版本号。
- **FR-010**：只有代码位置和已核实的事实都在时才能发 Error；缺位置或缺事实时，不发这条 Error，最多发一条上下文不完整提示。
- **FR-011**：这一版只用“服务器主动推送”的方式发诊断；不实现、也不注册客户端主动拉取诊断的方法（`textDocument/diagnostic`、`workspace/diagnostic`）。

#### 补全（completion）

- **FR-012**：处理带文件地址和光标位置的补全请求，成功时返回标准补全名单（或标准补全列表）。每个候选必须有名字和种类；知道的详情、插入文字、替换范围也要带上，替换范围要刚好盖住光标前正在输的那个名字。
- **FR-013**：候选由光标位置的语法规则和已核实的语义可见性共同决定：只给这个位置语法允许、语义上看得见、且适用性已核实过的名字，包括当前可见的声明、已索引的依赖或头文件符号、标准 C++ 关键字、已核实的宏和 Tops 内建变量；不能按固定类别列白名单，也不能凭空造出接口名或宏名。
- **FR-014**：候选不能来自过期或已失效的分析结果；重复候选要合并或按固定顺序排；同样输入每次候选顺序一致。
- **FR-014a**：文件已打开但最新分析还没完成时，补全名单只含一条提示项，它的名字和详情说明“正在分析中”，种类用标准补全种类里的“文本”类，不插入文字、替换范围为空；不得同时返回真实候选。
- **FR-015**：光标在注释、字符串里、或判断不了语义的区域时，返回空名单，不能给猜测结果。
- **FR-016**：这一版不做成员访问补全（点号后面的成员）、自动导入、代码片段、重载排序、文档渲染、跨仓符号搜索；这些场景没实现时返回空名单，不要报错。
- **FR-017**：补全返回空的名字叫“空名单”；文件没打开时返回空名单；文件已打开但最新分析还没完成时返回一条“正在分析中”提示项且不等分析做完；参数不对或位置超出文件范围时返回 `InvalidParams`；请求被取消时返回“请求已取消”错误；只有旧结果可用时返回空名单。
- **FR-018**：初始化时必须声明支持补全；不能声明还没实现的能力（比如补全项二次解析），也不能声明暗示支持成员补全的触发字符。

#### 悬停（hover）

- **FR-019**：处理带文件地址和光标位置的悬停请求。成功时返回名字出现的范围和一段可读说明；说明格式看编辑器初始化时声明支持什么：支持 Markdown 就用 Markdown，只支持纯文本就用纯文本。
- **FR-020**：悬停内容必须有名字和种类；知道的时候要带上类型或函数签名、声明位置；Tops 名字要写明用的哪个 profile、哪个 pass，并分开标注标准 C++ 结论和 Tops 扩展结论。
- **FR-021**：悬停只能写已核实的结论；上下文不完整时要标明“降级”，不能把缺信息时的推测写成确定结论。
- **FR-022**：光标在注释、字符串、空白、或解析不出名字的位置时，返回空结果。
- **FR-023**：文件没打开或名字解析不出来时返回空结果；文件已打开但最新分析还没完成时，返回一条“正在分析中”的提示，不能返回空结果、不能报错、也不能等分析做完；参数不对或位置超出范围时返回 `InvalidParams`；请求被取消时返回“请求已取消”错误；只有旧结果可用时返回空结果。
- **FR-024**：初始化时必须声明支持悬停。

#### 已有导航功能（跳定义、查引用、列符号）

- **FR-025**：跳定义返回一个或多个声明位置，解析不出来时返回空结果；查引用返回位置名单，没人用就返回空名单；列文档符号返回符号名单，没符号就返回空名单。
- **FR-025a**：跳定义、查引用、列符号在最新分析还没完成时，最多等 2 秒；2 秒内分析完成就正常返回结果；超过 2 秒仍未完成时返回标准 `ContentModified` 错误，不返回空结果，也不无限等待。
- **FR-026**：跳定义、查引用、列符号、补全、悬停、诊断，必须基于同一份最新分析结果；不能把不同文档版本、不同上下文版本或不同 pass 的结果拼在一起返回。
- **FR-027**：文件没打开、参数不对、请求取消、只有旧结果这四种情况，已有的跳定义、查引用、列符号要和新增的补全、悬停按同一套规则处理；唯一的差异是分析进行中时，导航按 FR-025a 等待并可能返回 `ContentModified`，补全和悬停则立即返回“正在分析”提示。
- **FR-028**：导航结果要保留已有的来源记录；结果受目标配置影响时，要写明对应的 profile 和 pass。

#### 能力声明与协议规则

- **FR-029**：初始化时只声明这一版真正支持的能力：跳定义、查引用、列符号、补全、悬停、推送诊断；不能声明拉取诊断、补全二次解析、工作区符号等没实现的能力。
- **FR-030**：所有已实现请求都用标准字段和标准错误码；语义状态不能塞进自定义响应字段，允许的附加信息只能放在标准诊断附加字段或标准补全项附加字段里。
- **FR-031**：未实现或未知的方法一律返回标准 `MethodNotFound`；没初始化和正在关闭的状态，沿用现有生命周期错误行为。
- **FR-032**：日志要能看出请求结果属于哪类（成功、空结果、参数错误、取消、丢弃过期结果），并带上文件标识、版本、编号；不能记完整源码或凭据。

#### 验收材料

- **FR-033**：自动化验收至少三个测试文件：一个能正常分析的 Tops kernel、一个标准 C++ 写错的文件、一个 Tops 规则写错的文件；三个文件都以固定文件的形式放在测试数据目录，测试代码读取文件内容，不把源码内联在测试代码里；三个文件都通过启动真实服务器进程的端到端测试驱动，不另建只跑内部函数的测试。
- **FR-034**：每个测试文件都要写清楚诊断、补全、悬停、跳定义、查引用、列符号的预期结果，并覆盖适用的空结果、错误、取消、过期场景；验证方式统一为端到端会话，不另建包内单元测试。
- **FR-035**：正常 kernel 不能出现意料之外的 Error；两个错误文件要报出预期的编号、位置、级别和来源记录，不能混进无关的 Error。
- **FR-036**：把测试文件改成新版本后，要验证旧诊断被清掉、旧补全和旧悬停不再出现、新结果对应当前版本。
- **FR-037**：验收要在没有 GCU 硬件、也不需要跑 Clang 的条件下能重复执行。

### 涉及的数据

- **一次请求**：客户端发过来的补全、悬停、跳定义、查引用或列符号，包含要干什么、哪个文件、光标在哪、客户端提供了什么上下文。
- **一次分析的结果**：某个文件在某个文档版本、某个上下文版本下算出来的东西，包括符号、错误、类型。所有返回值都必须绑定到同一份结果。
- **一条诊断**：用户能看到的一条问题，包含编号、代码位置、严重级别、文字、来源类别、来源记录。
- **一个补全候选**：名单里的一项，包含显示的名字、种类、已知详情、插入文字、替换范围、来源。
- **悬停结果**：光标处名字的说明信息，包含范围、名字、种类、已知类型或签名、声明位置、来源、上下文状态。
- **上下文**：决定 Tops 规则适不适用的信息，包含 profile、pass、来源记录，状态分四种：`resolved`（信息齐全）、`partial`（只有一部分）、`missing`（没有）、`invalid`（互相矛盾）。
- **测试文件（fixture）**：三个场景文件，以固定文件形式放在测试数据目录，以及每个文件对应的预期结果；测试代码读取文件内容，用来验证正常、空结果、错误、取消、过期这几类行为。

## 成功标准

以下每项都可以直接检查，不需要知道具体怎么实现。

- **SC-001**：六个功能（诊断、补全、悬停、跳定义、查引用、列符号）的行为用例 100% 通过，包括正常、空结果、参数错误、取消、过期五类；所有用例都通过端到端服务器会话执行。
- **SC-002**：三个测试文件的预期诊断 100% 命中；正常 kernel 里意料之外的 Error 为 0 条；两个错误文件里混进的无关 Error 为 0 条。
- **SC-003**：测试文件里所有可见的声明名字，补全名单中出现它的比例为 100%；所有能解析的位置，悬停返回名字、种类、已知类型或签名的比例为 100%。
- **SC-004**：连续做 100 次“改文件、同时发请求”或“请求中途取消”，返回旧版本结果的次数为 0，发出旧版本诊断的次数为 0。
- **SC-005**：用户能在三个测试文件上完成“看提示 → 补全或悬停 → 改代码 → 再看提示”，全程不需要重启服务器；文件不超过 500 行时，改完 2 秒内能看到新提示。
- **SC-006**：文件没打开、没有候选、光标不在名字上这三类请求，返回约定空结果的比例为 100%，并且不报错、不卡住。
- **SC-007**：只支持基础能力的编辑器上，初始化返回里不包含任何没实现的能力；调没实现的方法 100% 返回 `MethodNotFound`。
- **SC-008**：验收运行的日志里不出现完整源码和凭据；丢弃过期结果和请求失败都能靠日志分类定位，比例为 100%。
- **SC-009**：文件已打开但最新分析还没完成时，悬停 100% 返回“正在分析中”提示，补全 100% 只返回一条同类提示项且不混入真实候选，两类请求都不报错、不阻塞；跳定义、查引用、列符号在 2 秒内分析完成时 100% 返回结果，超时则 100% 返回 `ContentModified`，不出现无限等待。

## 假设

- 跳定义、查引用、列符号在前一阶段已经做完。这一版把它们当成既有能力，只验证行为规则是否一致，不重新设计它们的含义。
- 推送诊断的链路已经有了。这一版补齐“四类诊断合并发布、版本规则、改好后清空、整套人工验收”，不引入拉取式诊断。
- 正常 kernel 使用 `resolved`（信息齐全）的上下文；测试文件直接给出 profile、pass 和来源记录，不依赖真实 GCU 硬件。
- 验收只跑端到端服务器会话；包内单元测试可以另行保留，但不作为本功能的验收依据，也不为这一版新写。
- 导航的等待上限固定为 2 秒，本版不提供客户端配置项；超时用标准 `ContentModified` 错误表示，由客户端决定是否重试。
- 三个验收文件以固定文件形式存放在测试数据目录，测试代码读取同一份文件，不另外内联一份源码。
- 补全这一版只处理单文件、已索引依赖或头文件里的可见名字、标准关键字、已核实的 Tops 构造。成员访问、自动导入、代码片段、重载排序、文档渲染留到以后。
- 悬停这一版只显示已核实的符号信息和上下文状态，不显示注释文档、外部网页或推测性说明。
- 位置换算、文件同步、启动关闭流程、消息分帧沿用已有约定；不改变客户端已有设置和命令。
- 多文件只使用已打开的文件和已索引的工作区/头文件；不扫描整个工作区，也不访问网络。
- 完整的性能指标、缓存冷热对比、跨版本兼容检查放到后续阶段；这一版只看测试文件规模下够不够快。
- 标准 C++ 规则和 Tops 规则的划分沿用已建立的语义基线；拿不到目标信息时，不出确定结论。
- 不新增外部依赖，也不提高工具链版本要求。
- 给用户看的文字（诊断消息、悬停内容、补全详情）与日志、错误信息统一使用英文；代码名、方法名、诊断编号保持原样。
